Where we are today

Three proposals

A
Code-controlled seed + exercise_id on logs
Recommended
The exercise library lives in code (packages/core), structured as muscleGroup → Exercise[] with stable IDs. Add one exercise_id column to logged slots so history is bound to a real exercise, not a renamable string.
  • ✓ Matches your firm rule exactly: exercises 100% code-controlled, versioned, ship-with-app, NO user-custom
  • ✓ Fast & offline — no DB round-trips, no RLS for static data
  • ✓ Stable history: a logged set keeps its exercise_id even if you rename a movement
  • ✓ 31 → 1500 exercises belong in code, not a user table
  • – "Adding exercises" = shipping code (which is exactly what you want)
1 tiny migrationno seedingyour NO-custom rule ✓

// packages/core muscleGroups = [chest, back, shoulders, arms, legs, core] exercises: Record<MuscleGroup, Exercise[]> chest: [ { id:"EIeI8Vf", name, equip, target, gif, poster, steps }, … ] // DB: one column added workout_slots.exercise_id text
B
Supabase tables (read-only seed)
Scales big
Put exercises and muscle_groups in Postgres as read-only seeded tables. The app queries them; slots & logs FK to exercise.id.
  • ✓ Server-side filtering/search — good if the library gets very large
  • ✓ Single source of truth in DB; referential integrity via real FKs
  • – Overkill now: migrations + seed scripts + RLS for data that never changes per-user
  • – Contradicts "code-controlled" — the library now lives in the DB
  • – Needs network for the catalog (worse offline)

  • – Denormalized name can drift from the live catalog label

★ My recommendation — Option A

Keep the exercise library in code (your firm rule), restructured as muscle group → specific exercise with stable exercisedb IDs. Add one small DB column so logged history is bound to a real exercise. It's the least effort, fastest, offline-first, and it's the only option that honours "exercises are 100% code-controlled, sessions are the customizable part."

  1. Restructure core: muscleGroups[] + exercises: Record<group, Exercise[]> (fold today's catalog + media map into one entity)
  2. Add exercise_id to workout_slots (migration 0007) — sessions/logs reference by ID
  3. Session slots point at an exercise ID; the "Add exercise" picker browses by muscle group
  4. Migrate existing text slots → IDs via a name map (one-time, keep text as fallback)
