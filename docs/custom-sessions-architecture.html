01 · THE PROBLEM

Base sessions live in code. Leon wants to change his.

Every base workout — "Push day", "Full Upper" — is defined in catalog.ts: versioned, shared by all users, and improved over time. So what happens when one user wants to add an exercise?

Push day catalog.ts · shared
🏋️Bench Press4 × 8
💪Overhead Press3 × 10
🔻Triceps Pushdown3 × 12

Leon loves this session — but he wants to add Incline Dumbbell Press to his Push day.

The naïve fix is to copy the whole session into the database so he can edit his own version. That one shortcut is where things quietly break. ↓

02 · THE FORK IN THE ROAD

Two ways to let users customize.

One creates a second source of truth that drifts forever. The other keeps a single source of truth and stores only what changed.

✕ The Trap · copy everything

Copy each session into the DB

Every user gets a full editable copy of every base session.

two sources of truth → divergence hell + bloat

Keep base in code, store only deltas

Base stays read-only & shared. A thin overlay holds just the changes.

03 · WHY IT STAYS CLEAN

Six things the overlay buys you.

✓

One source of truth

Base content lives in code. Improve "Push day" once — every user gets it instantly.

✓

The overlay is tiny

Only the deltas are stored: added, hidden, reordered. No full-session copies, no bloat.

✓

Merge is a pure function

effectiveSession(base, overlay) — deterministic, trivially unit-testable, no side effects.

✓

"Reset to default" is free

Just delete the overlay row. The user snaps back to the pristine base — no cleanup logic.

✓

Reuse the catalog

Added exercises can reuse existing catalog entries (images + cues) or be a custom typed name.

✓

Logging just works

Workouts already save arbitrary exercise slots, so logging an added exercise needs zero new plumbing.

04 · THE OVERLAY TABLE

The whole thing is one small table.

One row per (user, session). An empty row means pure base. Protected per-user with row-level security.

session_customizations.sql
-- one row per (user, session). empty row = pure base.
table session_customizations (
  user_id  uuid      -- who owns this overlay
  plan    text      -- which plan template
  sess    text      -- which session (e.g. "push")
  added   jsonb[]  -- exercises Leon added
  hidden  text[]   -- base exercises he removed
  order   text[]   -- optional reordering
)
-- 🔒 row-level security: a user only sees their own rows

06 · RECOMMENDED BUILD ORDER

Ship value fast, add the depth second.

A

The picker + one-off add

ships fast · no schema

  • Build the "Add exercise" picker (reuses the catalog)
  • Append to the live in-memory session
  • Save it with that workout log
  • Users get "add to today" immediately
B

Overlay + permanent

medium · needs the table

  • Add the session_customizations table
  • Write the effectiveSession() merge
  • Flip on the "permanently" toggle
  • Add remove / reorder + reset-to-default
◆ THE RECOMMENDATION

Base + Overlay. Start with Phase A.

Keep one source of truth in code, store only the deltas in a thin overlay, and merge them at read time. Ship the one-off picker first — then layer in the permanent overlay when you're ready. No divergence, no bloat, no regrets.
