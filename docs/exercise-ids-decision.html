Do exercises need
an ID?

Right now, an exercise is its name. That's fine — until it isn't. Here's every option, and what each migration actually costs, so you can decide.

IDs are the right long-term design. The only real question is WHEN — not IF. This doc exists so you time it deliberately, mid-feature.

01 · TODAY

The exercise's ID is its display name.

A slot is just a tuple — [name, scheme, force]. There's no separate identifier. Everything downstream matches on that one name string.

02 · THE RISK

Name-as-id has exactly four sharp edges.

None of them bite today. All of them exist because the name is doing two jobs at once — it's both what the user reads and the primary key.

!

Rename = data loss

Rename Flat chest press → Barbell Bench in code, and every logged workout, PR, and overlay still points at the OLD name. History silently splits — no migration path.

!

Custom name collision

A user-typed custom Bicep curl that matches a catalog key can merge or confuse. The name is the only identity, so it can't tell them apart.

!

Same name, shared history

Row in the gym plan and Row in the travel plan collapse into one history bucket. Two different exercises, one identity.

!

i18n is blocked

You can't translate a string that's also the primary key. Localizing the display name would orphan every record keyed to the English one.

◆

The key insight

The pain only appears when you rename a catalog exercise. As long as catalog names are frozen, name-as-id behaves identically to real IDs — same lookups, same history, same everything. Freezing the names buys you all the safety of IDs for zero work.

03 · THE OPTIONS

Three ways forward, from do-nothing to full refactor.

Same destination-readiness, very different price tags. Read across the effort / risk / value badges.

Current state
A
Keep name-as-id
Pragmatic. Do nothing structural — just add one rule.
Effort · None Risk · None now Value · Low
What it involves
  • Nothing structural
  • Treat catalog names as immutable IDs
  • To "rename": add a NEW exercise + migrate — never edit a name in place
Good when: personal / small app, you control the ~50-name catalog, one real user. This is where you are today.
B
Full stable-ID refactor
The proper foundation. Every layer moves from name → id.
Effort · 1–2 sessions Risk · Medium Value · High (later)
What it involves
  • Catalog gets stable slug IDs
  • DB backfill of live history (the delicate part)
  • Every name-lookup → id-lookup
  • Overlay + custom exercises use IDs
Good when: the app grows — multi-user, i18n, renamable exercises, a real exercise library. Low value right now.
◆ Recommended follow-up
C
Catalog IDs only
The cheap-insurance middle path. Stops the bleeding, no DB migration.
Effort · Small Risk · Low Value · High
What it involves
  • Add stable IDs to the catalog only
  • NEW writes store id alongside the name
  • OLD data stays name-based
  • A tiny name↔id resolver bridges both
Effect: all NEW data becomes id-safe without touching historical rows. Makes the full B backfill optional & low-stakes.
04 · INSIDE OPTION B

What the full migration actually involves.

Six steps. Five are mechanical. One — the live-data backfill — is the reason timing matters. It's flagged in red below.

1

Catalog: add stable slug IDs

Low risk

Give each exercise a stable id (e.g. flat_chest_press). Name becomes display-only; slots reference the id. ~50 exercises, scriptable.

2

Database: backfill live history

◆ The delicate part

workout_slots.slot is a text name today. Add workout_slots.slot_id and backfill by mapping name → id across ALL existing data — your 9 real workouts + test data.

⚠ Any name that doesn't map = orphaned history. Keep the old name column during transition for safety & reversibility.
3

Core: match on id, not name

Mechanical

Rewrite every name-match: fetchHistory, lastFor, lastKindFor, kindsLoggedFor, the personal_records SQL VIEW (regroup by id), the save_workout RPC, and the overlay functions.

4

Overlay: store IDs

Mechanical

The just-built added / hidden / ordering overlay stores ids instead of names.

5

UI: display name, logic id

Mechanical

Display uses the name, logic uses the id — mostly find-and-replace across TrainView, ExerciseCard, Progress, Calendar.

6

Custom exercises: generated UUIDs

Low risk

Custom exercises get generated uuids so they can never collide with a catalog id — closing risk #2 for good.

05 · THE MIDDLE PATH

Option C: id-safe new data, zero migration.

Add IDs to the catalog. New writes carry both id + name. Old rows keep their name only. A resolver bridges the two so lookups work across the seam.

◆ New writes (from now on)
flat_chest_press · "Flat chest press"id-safe
barbell_row · "Barbell row"id-safe
uuid:9f2a… · "My custom curl"id-safe
Old rows (unchanged)
"Flat chest press"name only
"Barbell row"name only
"Squat"name only
⇄   resolver: name ↔ id  — lookups match on either side, so old + new data read as one history
The effect: Option C stops the bleeding — every new record is id-safe — without migrating a single historical row. The full DB backfill (Option B, step 2) becomes optional and much lower-stakes later, because new data already has ids.
◆ THE RECOMMENDATION

Ship on names now. Insure with C. Backfill only when you need it.

1 NOW

Finish custom-sessions on names

Names are frozen ids in practice — behaves identically as long as nothing gets renamed. Don't stop mid-feature to migrate live data.

2 SOON

Do Option C as a small follow-up

Add catalog ids so all new data becomes id-safe. Cheap insurance, low risk, no historical migration.

3 LATER

Do the full B backfill on demand

Only when you actually need renames, an exercise library, or multi-user — not a moment before.

This is a reversible, incremental path — A → C → B — not a now-or-never decision. Each step stands on its own, and you can stop at any of them.
